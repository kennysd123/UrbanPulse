![Diagrama del estilo arquitectónico de UrbanPulse](<../diagramas/estilo-arquitectonico.png>)

UrbanPulse adopta un **monolito modular con principios de Clean Architecture**, organizado en cuatro capas: **Presentación, Aplicación, Dominio e Infraestructura**. La capa de aplicación coordina los casos de uso; el dominio concentra las reglas del negocio; y la infraestructura implementa las integraciones externas y la persistencia relacional mediante repositorios, sin motor ni ORM seleccionados. La API REST sirve como punto de entrada al backend, manteniendo los módulos organizados por responsabilidad.

Las dependencias de código se orientan al núcleo; Dominio no depende de Infraestructura. Se conservan ocho módulos, cinco contenedores internos y seis responsabilidades técnicas conceptuales en las [fuentes C1–C4 existentes](../04-modelo-c4/01-contexto-c1.md). Los PNG históricos permanecen pendientes de actualización; sus tecnologías no constituyen selección aprobada.

El proveedor financiero es externo: total o adelanto configurado para propietario receptor, con verificación backend y aplicación única; aprobación aislada no confirma. [ADR-012](../01-analisis-de-sistema/adr/ADR-012-modelo-pagos-mvp.md) sigue propuesta y Mercado Pago Marketplace Split 1:1 candidato sin validación. El catálogo contiene doce ADR; ADR-001–ADR-009 adoptadas y ADR-010/ADR-011 cerradas conceptualmente en sus ámbitos. Redis solo fichas públicas reconstruibles; RabbitMQ solo invalidaciones técnicas, con consumidor interno. Worker independiente: **Preparado arquitectónicamente, no obligatorio inicialmente**; implementación posterior. No se acredita integración o producción.
